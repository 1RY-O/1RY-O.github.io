01 FLAGSHIP · AUDIO-TO-NOTATION WORKFLOW

VI-071

Turn sound into something you can read.

An audio-to-sheet-music experiment built around the messy part of music transcription: turning a recording into structured notes, readable notation, and usable musical files. VI-071 brings audio processing, model inference, symbolic formats, and score rendering into one workflow.

I wanted to build more than a transcription demo. The interesting challenge was making the whole pipeline work — from audio input and model inference to notation that can be inspected, played, and exported. That meant working through model memory, backend jobs, file conversion, and the difference between a result that renders and a result that is musically accurate.

  • STACKReact · Vite · TS / Node · Express / Python / MuScriptor / FFmpeg / Verovio
  • OUTPUTSMIDI · MusicXML · rendered score + playback / export
  • FLOWJob-based transcription · CPU-only local experimentation

Pipeline intended workflow

  1. 1 · IngestAudio input + FFmpeg-based audio handling.
  2. 2 · TranscribePython worker runs MuScriptor inference as backend jobs.
  3. 3 · SymbolizeOutput becomes MIDI and MusicXML symbolic music.
  4. 4 · RenderVerovio score rendering + inspection, playback, export.

Described from the documented design. Inspect project code before treating every stage as fully implemented or production-ready.

Engineering work what was actually done

  • Python transcription worker integrated with a TypeScript backend.
  • Job-oriented backend processing and status handling.
  • MIDI and MusicXML symbolic output formats.
  • Score rendering + audio-processing components.
  • CPU memory profiling across model-loading configs.
  • Streaming BF16 experiment to reduce peak memory.
  • Backend tests for core workflow behavior.
  • Latency, model limits, chunking, failure handling.

Measured experiment local CPU benchmark

On a local CPU benchmark, streaming BF16 reduced combined Node/Python peak memory from 1157.1 MB to 844.9 MB (~27%). Results are specific to the tested environment and workload.

VI-071 · MuScriptor model-loading on CPU — peak memory, measured locally
ConfigurationPython peakNode+Python peak
Legacy FP321080.2 MB1157.1 MB
Streaming FP321073.7 MB1149.8 MB
Streaming BF16 ★ selected766.9 MB844.9 MB
Streaming FP16762.8 MB836.6 MB
  • BF16 ≈ 27% lower combined peak than Legacy FP32 here (1157.1 → 844.9 MB).
  • FP16 measured slightly lower, but BF16 was selected: FP16 had slower generation + narrower dynamic range in this setup.
  • Synthetic piano-like melody parity applies to that test only — not arbitrary recordings.
  • KV cache affects memory; generation caps + chunking explored without quality claims until real-recording validation.
  • Local results — not universal guarantees.

Separate later run (setup unverified): approximately 690 MB combined peak was reported for a later optimized run. Its measurement method and environment are not confirmed comparable to the table above, so it is presented here separately — not merged into the comparison. Neither result is a production-performance claim, and neither establishes general transcription accuracy.

Limitations: transcription accuracy and long-recording reliability remain active evaluation areas. Synthetic test parity does not establish accuracy on arbitrary music.
