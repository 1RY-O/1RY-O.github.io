Engineering what was actually built

  • Python transcription worker integrated with a TypeScript backend.
  • Job-oriented backend processing and status handling.
  • MIDI and MusicXML symbolic output formats.
  • Score rendering plus audio-processing components.
  • CPU memory profiling across model-loading configurations.
  • Streaming BF16 experiment to reduce peak memory.
  • KV-cache adjustments and FlashAttention trials.
  • ONNX inference and INT8 quantization evaluated — not adopted after an unacceptable accuracy trade-off in testing.
  • Cloudflare Tunnel used to reach the development worker.
  • Backend tests for core workflow behaviour.

Measured experiment local CPU benchmark

Streaming BF16 cut combined Node + Python peak memory from 1157.1 MB to 844.9 MB — roughly 27% — on a local CPU benchmark.

MuScriptor model-loading on CPU · peak memory, measured locally
ConfigurationPython peakNode + Python
Legacy FP321080.2 MB1157.1 MB
Streaming FP321073.7 MB1149.8 MB
Streaming BF16 ★ selected766.9 MB844.9 MB
Streaming FP16762.8 MB836.6 MB
  • FP16 measured slightly lower, but BF16 was selected: FP16 showed slower generation and a narrower dynamic range in this setup.
  • Synthetic piano-like melody parity applies to that test only — not arbitrary recordings.
  • Local results for the tested environment and workload — not universal guarantees.

Separate later run — setup unverified: approximately 690 MB combined peak was reported for an optimized run, down from an earlier ~1.15 GB baseline. Its measurement method and environment are not confirmed comparable to the table above, so it is presented separately and not merged into the comparison.

Limitations: transcription accuracy and long-recording reliability remain active evaluation areas. Synthetic test parity does not establish accuracy on arbitrary music. Current state: active experiment, CPU-only local work. No public demo URL is claimed — a deployment address appears in the repository resources but its working state is unverified.
